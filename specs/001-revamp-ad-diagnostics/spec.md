# Feature Specification: 广告异常诊断重构

**Feature Branch**: `001-revamp-ad-diagnostics`  
**Created**: 2026-09-03  
**Status**: Draft  
**Input**: User description: "需要大改广告异常诊断这个模块"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按负责人、店铺和产品发起可信诊断 (Priority: P1)

运营人员在独立诊断工作台选择负责人、店铺、产品和分析周期后发起诊断，获得按影响程度排序的异常、每项异常的业务证据、已验证归因和仅供人工处理的建议。运营人员能够区分事实、合理假设与数据不足，不会把不完整或冲突的数据误认为确定结论。

**Why this priority**: 可信、可行动的诊断结果是该模块存在的核心价值；其余体验改进均依赖该结果。

**Independent Test**: 使用包含已知异常、完整证据和不完整证据的广告数据分别运行诊断，验证每项结果的证据状态、结论边界和建议均符合预期。

**Acceptance Scenarios**:

1. **Given** 运营人员已选择负责人、店铺、产品、当前期和可选对照期，**When** 完成一次诊断，**Then** 系统仅展示该筛选范围内的异常对象、影响程度、量化证据、已验证原因和建议处理动作。
2. **Given** 缺少验证某种趋势所需的可比数据，**When** 系统完成诊断，**Then** 系统将该原因标为数据不足或待验证，不输出确定性的趋势结论或高风险建议。
3. **Given** 同一对象存在相互冲突的证据，**When** 系统完成诊断，**Then** 系统展示冲突及其来源，并将建议降级为观察或补查。
4. **Given** 运营人员打开诊断工作台，**When** 选择店铺，**Then** 系统提供该店铺对应的负责人和可诊断父 ASIN 选项；负责人仅在人工筛选界面可见。

---

### User Story 2 - 高效审阅和处理运营代办 (Priority: P2)

运营人员可以在一次诊断结束后按负责人、店铺、产品、严重程度、异常类型和处理状态查看代办；每个代办均能回溯到对应异常和证据，并可由运营人员标记为已审阅、已完成或不采纳。

**Why this priority**: 诊断只有进入日常工作流，才能减少无效花费和漏处理问题。

**Independent Test**: 完成一次含多个异常的诊断，验证用户能筛选代办、打开关联证据并更新处理状态；相同问题不会生成重复代办。

**Acceptance Scenarios**:

1. **Given** 已完成的诊断包含可处理建议，**When** 运营人员查看代办，**Then** 每项代办显示建议、风险、优先级、负责人待办状态和可追溯证据。
2. **Given** 同一问题在重复诊断中仍然存在，**When** 系统生成代办，**Then** 系统更新或关联已有待办，而不是创建重复项。
3. **Given** 运营人员选择不采纳一项建议，**When** 保存处理结果，**Then** 系统保留决定及理由，并不改变任何广告设置。

---

### User Story 3 - 管理安全且可持续的诊断范围 (Priority: P3)

业务管理员可以为诊断设定负责人、店铺、产品、周期、业务目标和运行方式；系统仅在授权范围内分析数据，并提供清晰的运行进度、失败原因和可重试状态。

**Why this priority**: 多店铺和周期性诊断必须可控，才能避免无边界的数据访问与不透明失败。

**Independent Test**: 以不同店铺、不同周期及一次数据源不可用的情形发起诊断，验证范围限制、进度显示和恢复提示。

**Acceptance Scenarios**:

1. **Given** 管理员选择了负责人、店铺、产品和周期，**When** 发起诊断，**Then** 结果仅包含所选范围内的数据，并记录本次诊断范围。
2. **Given** 某类必要数据暂时不可取得，**When** 诊断运行，**Then** 系统显示受影响阶段、数据限制和下一步选择，不把失败显示为“无异常”。
3. **Given** 诊断被再次提交且范围相同，**When** 系统识别为重复请求，**Then** 系统避免产生重复运行或重复代办。

### Edge Cases

- 当前周期没有广告活动或没有足以评估的花费、点击数据时，系统明确显示“数据不足”，而不是给出正常或异常结论。
- 周期不具可比性、币种不一致或店铺授权失效时，系统阻止不可靠比较并说明原因。
- 报告分页、部分数据缺失或重复记录时，系统保留覆盖范围和数据完整性状态，避免重复计数。
- 单次诊断中达到查询额度或外部数据源限流时，系统保留已验证结果并明确哪些归因未完成。
- 不可信的广告名称、搜索词或外部文本包含指令性内容时，系统仅将其作为业务数据，不将其视为系统指令。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在独立诊断工作台中支持由运营人员发起、并可配置为周期性运行的广告异常诊断；每次运行必须选择负责人、店铺、产品和分析周期，并记录业务目标和发起方式。
- **FR-002**: 系统必须按“数据巡检、问题归因、策略建议、复核与代办”的业务阶段展示可理解的进度和终态。
- **FR-003**: 系统必须基于实际取得的数据识别并量化广告异常；所有比率指标必须在分母为零或数据缺失时给出明确状态。
- **FR-004**: 系统必须将每个异常关联到可追溯的证据，至少包含分析对象、指标、时间范围、数据完整性状态和证据来源。
- **FR-005**: 系统必须仅将已验证的数据表述为事实；未验证解释必须标记为假设或数据不足，并且不能单独支撑高风险建议。
- **FR-006**: 系统必须在有可比期间数据时才输出有关成本、转化或竞价变化的趋势结论；没有可比数据时仅输出当前期事实。
- **FR-007**: 系统必须按影响程度优先处理异常，并对下钻查询设置边界；当无法取得完整明细时，必须报告未覆盖范围。
- **FR-008**: 系统必须为每项建议说明目标对象、建议动作、预期影响、风险和依据；建议不得直接改变广告预算、竞价、状态、关键词或投放。
- **FR-009**: 系统必须检测同一对象上的冲突建议和重复代办，并要求人工确认后才能将代办标记为已完成。
- **FR-010**: 系统必须保留一次诊断从异常、证据、归因、建议到代办处理状态的完整追溯关系。
- **FR-011**: 系统必须在数据不可用、授权受限、请求受限或运行中断时提供明确失败原因，并允许在不重复产生已确认结果的前提下恢复或重试。
- **FR-012**: 系统必须只处理用户获授权访问的负责人、店铺、产品和相关数据，并将来自外部数据源的文本作为不可信业务数据处理。
- **FR-013**: 系统必须仅将负责人信息用于界面筛选、访问范围判定和人工运营分配；在 AI 上下文、诊断结果、代办内容、导出内容和日志中必须排除负责人姓名、联系方式及其他直接身份标识。若跨记录关联确有必要，仅可使用不可反推的替代标识。
- **FR-014**: 系统必须将本次诊断的归因范围限定在广告层级，包括广告活动、广告组、关键词、投放和搜索词；商品表现、库存、利润及 Listing 的跨域归因不属于本次范围。
- **FR-015**: 系统必须优先通过领星开放接口获取广告诊断的核心报表；仅在开放接口未覆盖所需的只读能力时，才可使用受控的领星 MCP 补充数据。诊断推理过程不得直接获得无限制的数据查询或任何广告修改能力。
- **FR-016**: 系统必须以独立诊断工作台作为主要入口，并支持按负责人、店铺和产品筛选可诊断范围及已有结果。
- **FR-017**: 系统必须提供一个内部选择数据 MCP，将“按店铺查询负责人和父 ASIN”的上游结果转换为工作台所需的最小选择目录。目录至少支持店铺、负责人、父 ASIN 及其确定性关联关系。
- **FR-018**: 内部选择数据 MCP 仅可由工作台的数据服务调用，不得作为 AI Agent 的可调用工具注册或透传其原始结果。负责人仅向有权限的人工用户显示；诊断请求和 AI 可见数据仅使用无身份语义的范围引用。

### Key Entities

- **诊断运行**: 一次指定范围和周期的诊断任务，包含运行状态、阶段进度、数据限制和追溯标识。
- **诊断范围**: 用户授权的负责人、店铺、产品、广告对象、分析周期、可选对照周期、经营目标和异常阈值；负责人身份信息仅用于人工界面和权限范围。
- **选择目录**: 用于工作台筛选的店铺、负责人和父 ASIN 的最小数据集，包含范围关联和不可识别的内部引用；不属于诊断证据或 AI 输入。
- **异常**: 在指定范围内被量化识别的广告表现问题，包含严重程度、影响、证据状态和关联对象。
- **证据**: 支撑异常或归因的数据事实，包含来源、范围、时间、完整性和可追溯引用。
- **归因结论**: 对异常原因的解释，明确区分已验证事实、待验证假设和数据不足。
- **建议**: 基于已验证归因生成的人工可审阅处理方案，包含风险、预期影响和必要证据。
- **运营代办**: 可分配、可去重、可追踪处理状态的建议工作项，不等同于实际广告操作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在完整且已授权的数据可用时，90% 的手动诊断在 5 分钟内向运营人员展示最终结果或明确的数据限制。
- **SC-002**: 抽样复核中，100% 的确定性异常和已验证归因可追溯到至少一条包含对象、指标和周期的证据。
- **SC-003**: 抽样复核中，0 个缺少可比数据的结果被表述为成本、转化或竞价的确定性趋势。
- **SC-004**: 同一诊断范围在 24 小时内重复运行时，重复运营代办比例不超过 2%。
- **SC-005**: 抽样复核中，负责人姓名、联系方式和直接身份标识在 AI 可见数据、诊断结果、代办、导出和日志中的泄露率为 0%；仅有权限的人工用户可在工作台筛选目录中查看负责人信息。
- **SC-006**: 试运行期间，至少 90% 的运营人员可在不查看原始报表的情况下定位一项高优先级异常的原因、依据与下一步处理方式。

## Assumptions

- 第一阶段继续遵守“只建议、不执行”的业务边界；任何广告写入能力不属于本次范围。
- 广告活动、广告组、关键词、投放和搜索词等核心广告报表具备可用的领星开放接口；未覆盖的只读数据能力可继续通过受控 MCP 提供。
- 领星 Open API 的店铺与 Listing/产品数据能力可供内部选择数据 MCP 调用；该 MCP 负责数据转换和字段白名单，而不是将上游原始响应交给工作台或 AI。
- 本期不会将商品、库存、利润或 Listing 数据用于广告异常归因；后续若扩展这些领域，应作为独立功能范围重新确认。
- 当前诊断的四阶段业务顺序、现有用户认证和店铺授权机制可继续沿用，除非经范围确认后另行调整。
- 用户可选择当前期；提供对照期时才进行趋势比较。
- 无法完整获取数据时，优先交付有明确限制标记的已验证结果，而不是编造完整诊断。
- 历史诊断与代办需要在重构后仍可查看和追溯；具体迁移范围将在计划阶段确认。
