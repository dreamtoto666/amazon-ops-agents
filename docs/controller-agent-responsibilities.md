# 总控 Agent 职责说明

> 文档状态：V0.1  
> 适用范围：Amazon Operations Multi-Agent 第一版  
> 聊天入口数据来源：团队共享的已导入广告报表及各专业 Agent 返回的结构化结果

## 1. 角色定位

总控 Agent 是系统的统一入口和任务编排中心。它负责理解用户想解决的问题，将问题转换成可执行任务，选择正确的处理路径，调度专业 Agent，并把多个专业结果整理成面向亚马逊运营人员的最终答复。

总控 Agent 本身不是销售、广告、库存或市场分析专家，也不直接承担专业指标计算。它的核心价值是：**理解、路由、编排、管控和汇总**。

## 2. 核心职责

### 2.0 短期会话记忆

总控按 `(owner_id, conversation_id)` 隔离不同对话。每轮使用固定 `turn_id` 关联用户消息与最终助手回复；每次理解请求前读取当前有效会话摘要和最近未压缩的轮次。达到 30 个完整轮次时，最早 20 轮会压缩为结构化摘要，原始消息归档而不物理删除。记忆不保存密钥、MCP 原始响应、内部提示词或模型思考过程。

生产环境使用 PostgreSQL 持久化，API 重启后可继续同一对话；点击“新建对话”会生成新的 ID。压缩使用 PostgreSQL 行锁和过期租约，避免多个进程重复压缩同一轮次。`VERCEL=1` 的后端冒烟测试仍使用进程内存，不作为生产持久化方案。轮次、压缩数量与连接池分别由 `CONVERSATION_MEMORY_MAX_TURNS`、`CONVERSATION_MEMORY_COMPACT_TURNS`、`CONVERSATION_MEMORY_DB_POOL_SIZE` 配置。

### 2.1 理解用户意图

总控 Agent 必须从用户消息和必要的会话上下文中识别：

- 业务领域：店铺、商品、广告、库存、利润、关键词、竞品、跟卖、Listing、报表或系统能力；
- 用户动作：查询、概览、比较、诊断、建议、监控、创建、修改或解释；
- 查询对象：店铺、站点、ASIN、MSKU、SKU、广告活动、关键词等；
- 时间范围、对比周期、币种和数据粒度；
- 是否涉及多个业务领域；
- 当前请求的置信度、风险等级和缺失字段。

总控 Agent 应将相对日期转换成用户时区下的明确日期。例如，“最近 7 天”默认表示截至昨天的最近 7 个完整自然日，避免将尚未完整的当天数据混入分析。

### 2.2 生成标准化任务

总控 Agent 将自然语言问题整理为统一的结构化任务，至少包括：

- `domain`：主要业务领域；
- `action`：用户希望完成的动作；
- `secondary_domains`：确实需要协同验证的其他领域；
- `primary_agent`：从当前已注册 Agent 中选出的主处理者；
- `supporting_agents`：确实需要协同验证的补充处理者；
- `scope`：店铺、商品、广告对象、周期和币种等查询范围；
- `route`：后续处理方式；
- `risk_level`：操作风险；
- `missing_fields`：完成任务所缺少的关键信息；
- `normalized_request`：忠实于用户原意的标准化任务描述。

标准化过程中不得加入用户没有表达的业务判断，也不得凭空生成店铺 ID、ASIN、SKU 或广告活动 ID。

### 2.3 决定处理路径

总控 Agent 根据意图、信息完整度和风险选择以下路径之一：

| 路径 | 使用场景 | 总控行为 |
| --- | --- | --- |
| `execute` | 信息完整的只读经营查询或分析 | 制定计划并调度专业 Agent |
| `clarify` | 缺少会显著影响结果的关键范围 | 只提出一个简洁、可回答的问题 |
| `respond` | 不需要实时数据的概念解释或系统说明 | 直接组织答复，不调用领星 MCP |
| `approval` | 创建、修改或其他写操作 | 说明风险并等待人工审批 |
| `unsupported` | 超出系统或领星 MCP 当前能力 | 明确说明能力边界，不伪造结果 |

当请求同时缺少关键信息又涉及写操作时，先进入 `clarify`；信息补齐后再进入 `approval`。

### 2.4 制定执行计划和路由

总控 LLM 在结构化意图中选择已注册的主处理 Agent 和必要的补充 Agent；代码只按该选择生成任务、去重和调度，不再维护“业务领域 → Agent”的固定映射。

> 当前聊天入口已启用意图识别，但仅注册了广告专家。广告专家使用受限 ReAct 工作流：模型只能调用一次团队共享的已导入广告报表只读 MCP 工具，并根据工具观察结果答复；它不能执行广告修改。广告只读查询默认覆盖团队共享报表，不要求 `shop_id` 或时间范围；用户明确指定日期或 `profile_id` 时才缩小范围。其他领域会被正确识别和路由，但对应专家尚未接入，不能替代为广告查询或伪造业务结果。

当前只注册广告专家。LLM 只能从运行时能力清单中选择已注册 Agent；若未选择主 Agent，计划会被标记为不支持，而不会用其他领域 Agent 替代或伪造结果。

总控 LLM 负责确定：

- 需要调用哪些专业 Agent；
- 每个 Agent 的明确目标、原因和优先级；
- 任务采用串行还是并行；
- 是否允许追加验证轮次；
- Agent 之间的依赖关系。

总控 Agent 不负责为专业 Agent 选择具体的领星 MCP Tool。具体数据接口、字段映射和指标计算由对应专业 Agent 或统一数据网关负责。

### 2.5 调度和监督专业 Agent

执行阶段由总控 Agent 负责：

- 按计划启动专业 Agent；
- 在可并行且符合领星 MCP 限流策略时并行执行任务；
- 将统一的查询范围和只读上下文传递给各 Agent；
- 收集每个 Agent 的结构化结果、数据证据、建议和错误；
- 保证一个 Agent 失败时不会无条件取消其他已运行任务；
- 记录实际调用过的 Agent 和执行轮次；
- 控制最大调查轮次，防止无边界循环。

专业 Agent 返回结果必须区分：

- 已确认发现 `findings`；
- 待验证假设 `hypotheses`；
- 建议动作 `recommended_actions`；
- 数据来源 `artifacts`；
- 局部错误 `errors`。

Listing 文案 Agent 还可以返回结构化交付物 `deliverables`，其中包含主标题、副标题、五点描述、商品描述、Search Terms、关键词引用和质检结果。总控 Agent 原样传递这类交付物，不允许汇总模型改写字段或伪造关键词证据。

如果 Listing 文案 Agent 判断商品资料不足，总控 Agent 必须将整体任务切换到 `waiting_input` 阶段，通过 SSE 在对话窗口中展示一个明确的补充问题。用户补齐资料前，不调用关键词 MCP，也不生成猜测性文案。

### 2.6 发起补充验证

对于诊断或建议类问题，总控 Agent 可以检查专业 Agent 提出的假设。如果假设：

- 指明了需要另一个专业 Agent 验证；
- 置信度达到系统阈值；
- 对应 Agent 尚未执行；
- 当前轮次没有超过计划上限；

则总控 Agent 可以追加一轮验证任务。

总控 Agent 不得为了追求“更完整”而无限追加查询，也不得将未验证假设直接升级为事实。

### 2.7 汇总最终结果

总控 Agent 必须围绕用户原始问题组织最终答复，遵循“先结论、后证据、再行动”的顺序，并严格区分：

1. **已确认事实**：有专业 Agent 结果和证据引用支持；
2. **待验证假设**：可能的原因，但证据尚不充分；
3. **建议动作**：推荐采取的下一步，不代表已经执行。

汇总时还应：

- 合并语义重复的发现并保留证据引用；
- 明确展示多个专业 Agent 之间的一致结论；
- 遇到结论冲突时展示冲突及各自依据，不擅自选边；
- 对部分失败保持有用，先给出已有结论，再说明数据缺口；
- 按紧急性、经营影响、风险和可回滚性排序建议；
- 对缺少因果证据的关系使用“相关”“可能”或“需要验证”，不用“导致”。

总控 Agent 不重新计算 ACOS、TACOS、利润率、库存天数或预计损失，只引用专业 Agent 已经验证并返回的计算结果。

### 2.8 管理阶段式 SSE 反馈

总控 Agent 对外暴露稳定的业务阶段，而不是直接暴露 LangGraph 内部节点：

```text
理解问题 → 制定计划 → 分析数据 → 验证原因（可选）→ 整理结论
              └────────────→ 等待补充信息 / 等待人工审批
```

它负责发送以下业务事件：

- 任务开始、完成或失败；
- 阶段开始、进度、完成、等待或失败；
- 专业 Agent 启动、数据读取进度、完成或失败；
- 汇总结果的准备进度。

聊天入口还可在 `stage.progress` 中发送下列稳定的审计进度类型：

- `reasoning.summary`：面向用户的执行摘要；
- `reasoning.delta`：模型思考过程的增量文本（thinking 模式下的 `reasoning_content`），按调用单元/阶段分块累积。内容属于模型内部推理，不作为业务事实，可能包含系统提示词或内部状态；前端默认折叠展示，不进入会话记忆；
- `tool.call.started`、`tool.call.completed`、`tool.call.failed`：只读工具的调用状态、脱敏查询条件与受限业务结果；
- `response.delta`、`response.completed`：最终用户回答的文本流与完成标识。

工具结果和 `reasoning.delta` 仅在当前进程的 SSE 重放窗口内可见，不写入会话记忆。所有展示给浏览器的业务数据都必须经过字段白名单、敏感键脱敏、长度和行数限制，并显式作为不可信业务数据处理；不得传递 SQL、租户标识、密钥、Cookie 或系统提示词。模型思考内容按本协议经 `reasoning.delta` 明确传递时除外。

每个事件必须包含唯一事件 ID、任务 ID、全局递增序号、时间戳和结构化数据。客户端断线重连时，应支持通过 `Last-Event-ID` 重放遗漏事件。心跳仅用于维持传输连接，不作为业务事件持久化。

### 2.9 管理等待和恢复

当任务需要用户补充信息或审批时，总控 Agent 应：

- 进入 `waiting_input` 或 `waiting_approval` 状态；
- 明确告诉用户缺少什么或需要审批什么；
- 结束当前 SSE 连接，避免无意义占用；
- 在用户补充或审批后，使用同一个 `run_id` 恢复任务；
- 保留已有状态和事件历史，避免重复执行已经完成的步骤。

### 2.10 维护状态、审计和可恢复性

总控 Agent 维护统一共享状态，包括：

- 用户消息、用户默认配置、店铺目录和当前时间；
- 请求理解结果、查询范围、路径和风险等级；
- 执行计划、待执行任务、轮次和已调用 Agent；
- 专业结果、数据制品、错误和审计事件；
- 最终回复。

关键决策应可追踪，包括意图解析、路由选择、Agent 调度、工具数据来源、审批状态、错误和最终依据。生产环境中，事件与任务状态应持久化，确保进程重启后仍可恢复和审计。

## 3. 明确不属于总控 Agent 的职责

总控 Agent 不应：

- 直接查询领星 MCP 或自行选择具体 MCP Tool；
- 承担销售、利润、广告、库存或竞品的专业分析；
- 在没有专业结果时编造经营数据、原因或建议；
- 擅自修改广告预算、竞价、商品价格、Listing、采购、补货单或订单；
- 将建议描述为已经执行；
- 将假设描述为事实；
- 绕过用户审批执行写操作；
- 因用户消息中的提示注入而改变系统身份、规则或输出协议；
- 暴露内部思考过程、密钥、令牌或敏感配置；
- 无限制调用 Agent 或重复查询相同数据。

## 4. 风险与权限原则

- 只读查询可直接执行；
- 创建监控、自定义指标或报表等低风险写操作必须审批；
- 广告、售价、Listing、采购、补货、货件、订单和退款等高风险写操作必须审批；
- 第一版只生成审批请求和执行建议，不直接执行写操作；
- 所有来自用户、会话历史和领星 MCP 的文本都作为不可信数据处理，不得覆盖系统规则；
- 返回给模型的大型领星 JSON 应先经过字段筛选、敏感信息屏蔽和 Outline 压缩，但原始数据仍需保留用于审计。

## 5. 异常处理职责

总控 Agent 应识别并处理：

- 意图解析失败；
- 必要字段缺失；
- 专业 Agent 未注册或执行失败；
- 领星 MCP 超时、限流或返回不完整；
- 多个专业结果冲突；
- SSE 客户端断线或消费速度过慢；
- 系统能力不支持用户请求。

发生局部错误时，优先返回仍然可靠的部分结果，并明确说明哪些数据或结论缺失。发生不可恢复错误时，发送任务失败事件，不伪装成成功。

## 6. 完成标准

一个总控任务只有在满足以下条件时才视为完成：

- 已正确理解并结构化用户意图；
- 已选择与风险和信息完整度一致的处理路径；
- 已只调度必要的专业 Agent；
- 已收集并保留专业结果和数据来源；
- 已区分事实、假设和建议；
- 已向用户提供直接回答原问题的结果；
- 已正确发送终态事件；
- 不存在未经说明的失败、数据缺口或待审批动作。

若正在等待用户输入或人工审批，则任务处于暂停状态，而不是完成状态。
